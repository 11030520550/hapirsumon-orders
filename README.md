# מודעת — ניהול הזמנות פרסום בעיתון

אתר בעברית לניהול לקוחות, הזמנות פרסום וסטטוסי תשלום. לאחר הגדרת Supabase, לקוחות והזמנות נשמרים במסד נתונים משותף ומוגנים ב־Auth וב־RLS. נתונים מקומיים קודמים אינם נמחקים או מיובאים אוטומטית.

## הפעלה

1. לפני מעבר מגרסת `file://`, פתחו אותה במחשב שבו נשמרו הנתונים והורידו **גיבוי מקומי** ממסך ההתחברות. שמרו את קובץ ה־JSON במקום בטוח.
2. פתחו את `supabase-config.js` והדביקו את Project URL המאומת ואת מפתח `publishable` מהגדרות הפרויקט. לא להשתמש במפתח `secret` או `service_role`.
3. ודאו שב-Supabase ההרשמה הציבורית כבויה, שהטבלאות וה-RLS הוקמו, שפונקציית בדיקת ההרשאה קיימת, ושהמשתמש נוסף לרשימת `private.approved_users`. פרטים ב־[`SUPABASE-SETUP.md`](./SUPABASE-SETUP.md).
4. מתיקיית הפרויקט הפעילו `python -m http.server 8000` ופתחו `http://localhost:8000` בדפדפן עדכני. אין לפתוח את האתר ב־`file://`.
5. התחברו עם כתובת הדוא״ל והסיסמה של משתמש שהוזמן ואושר. אין הרשמה מתוך האתר.
6. לחצו על **רשימת לקוחות** כדי לחפש, לצפות או לערוך לקוחות; **הוסף לקוח** יוצר לקוח חדש. מהטבלה ניתן לחפש ולסנן הזמנות ולעדכן תשלום.
7. כפתור **גיבוי וייבוא מקומי** מוריד גיבוי לפני כל בדיקת ייבוא. אם הגיבוי הוכן במחשב/מקור אחר, יש לאשר זאת ולבחור את הקובץ. הייבוא מציג כפילויות ומוסיף רק רשומות חדשות; הוא אינו מוחק או דורס נתונים, ואינו מתחיל עד אישור מפורש. במקרה של כשל חלקי, אפשר לבחור שוב את אותו הגיבוי כדי לבדוק מחדש אילו רשומות עוד חסרות.

### תצוגה מקדימה של הממשק העסקי החדש

במסך ההתחברות אפשר לפתוח **תצוגה מקדימה של הממשק החדש**. התצוגה משתמשת בנתוני דוגמה המוגדרים בקוד ואינה קוראת או כותבת נתונים עסקיים ב-Supabase או ל-`localStorage`. אפשר לבדוק חיפוש, כרטיסי לקוח, שדות הזמנה וחישובי סיכום; שמירת לקוח והזמנות חסומה עד להתקנת סכימת העסק וחיבור ה-RPC. מוצרי הדוגמה אינם כוללים מחירון מאומת ואינם נתונים לשימוש עסקי. מנגנון ההתחברות הקיים נשאר ללא שינוי.

### בדיקות RPC בפרויקט Supabase נפרד

הוראות הקמה לפי סדר, אישור משתמש הבדיקה, קובץ הגדרות מקומי מוחרג מ-Git ובדיקות RPC נמצאות ב-[`SUPABASE-TESTING.md`](./SUPABASE-TESTING.md). כלי הבדיקה אינו משתמש בהגדרות הייצור או במפתחות סודיים; אין להריץ את קובצי ההגירה בפרויקט הפעיל.

## סנכרון ועריכה מקבילה

לפני עדכון הקוד, הריצו פעם אחת את `supabase-reliability-migration.sql` דרך SQL Editor של Supabase. זו הגירה לא-הרסנית: היא מוסיפה `updated_at` ללקוחות ולהזמנות, מעדכנת אותו בשינוי ומפעילה Realtime לטבלאות. היא לא משנה רשומות ולא משנה RLS. בלי ההגירה, גרסת הקוד החדשה אינה יכולה להגן מפני דריסת עריכה מקבילה.

היישום מאזין לשינויים ב-Realtime, ובמקרה שהחיבור החי אינו זמין בודק עדכונים תקופתית. עדכון לקוח או הזמנה נעשה רק אם הגרסה שהמשתמשת פתחה עדיין עדכנית; במקרה של התנגשות מוצגת שגיאה ואין הצלחה מדומה. **הורדת גיבוי עדכני מהענן** מייצאת JSON בפורמט UTF-8. נתוני האתר אינם נשמרים ב-`localStorage`.

## עדכון האתר הקיים ב-Netlify

1. ודאו ב-Supabase שהגירת הסנכרון הורצה, RLS פעיל, ההרשמה הציבורית כבויה, ושכל משתמשת הוזמנה ואושרה.
2. השתמשו בתיקיית `orders-netlify-ready` שנוצרה לצד תיקיית הפרויקט. היא מכילה רק `index.html`, `styles.css`, `app.js` ו-`supabase-config.js`. אל תעתיקו לתוכה גיבויים, SQL, מסמכים פנימיים או נתוני לקוחות.
3. באתר Netlify הקיים `cute-macaron-aede92`, פתחו **Deploys → Deploy manually** והעלו את תוכן התיקייה. אין ליצור אתר חדש ואין לשנות את כתובת האתר.
4. לאחר אישור מפורש לפרסום, בדקו את האתר ב-HTTPS: התחברות כמשתמשת מאושרת, חסימה בחלון פרטי לא מחובר, רענון, הוספה/עריכה, סנכרון בין שתי לשוניות והתנתקות.

הקבצים המקומיים והכנת החבילה אינם מפרסמים דבר. אל תפרסמו לפני שהגירת ה-SQL הורצה ונבדקה.

מפתחות Supabase הם ציבוריים בקוד דפדפן רק אם הם מסוג publishable/anon ו-RLS מוגדר כראוי. לעולם אל תכניסו `service_role`, `secret` או סיסמת מסד נתונים לקוד או לקובץ שנשלח למשתמשים.
