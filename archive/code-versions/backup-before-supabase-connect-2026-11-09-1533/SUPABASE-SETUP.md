# הכנת Supabase למערכת ההזמנות

## מה נבדק

האתר עדיין לא מחובר לשרת. `app.js` שומר את כל המידע מקומית ב־`localStorage` תחת המפתח `modaat-newspaper-ads-v1`; המבנה הוא שתי רשימות, `clients` ו־`orders`. לכל לקוח יש `id`, `name`, `phone`, `email`. לכל הזמנה יש `id`, `clientId`, `date`, `section`, `amount`, `paymentStatus`, `notes`.

בבדיקה הנוכחית נמצאו 4 לקוחות ו־6 הזמנות, ללא מזהי לקוח או הזמנה כפולים, ללא הזמנות עם לקוח חסר, וללא סכומים לא תקינים. הסטטוסים הם 4 `paid` ו־2 `pending`. אין כרגע רשימת `payments` או היסטוריית עסקאות נפרדת.

## קובץ הסכימה

הקובץ [`supabase-schema.sql`](./supabase-schema.sql) מכין:

- `public.clients` — לקוחות; מזהי הטקסט המקוריים נשמרים.
- `public.orders` — הזמנות עם קשר ללקוח, תאריך פרסום, מדור, סכום, `payment_status` והערות.
- `public.payments` — יומן לתשלומים בפועל בעתיד. הוא נפרד מסטטוס ההזמנה, קריאה/הוספה בלבד; שינוי או מחיקה של רשומות תשלום חסומים.
- `private.approved_users` — רשימת משתמשים שאושרו ידנית. היא אינה זמינה ללקוחות API.

אין בקובץ מפתחות API או סודות. רק משתמש מחובר שמזהה המשתמש שלו נוסף במפורש לרשימת האישור יכול לקרוא או לשנות לקוחות והזמנות. משתמש אנונימי ומשתמש מחובר שלא אושר אינם מקבלים גישה דרך RLS. כל המשתמשים המאושרים עובדים עם אותו מאגר משותף.

## התקנה בפרויקט Supabase

1. היכנסי לפרויקט `orders` ובדקי שה־Database עדיין חדש או שאין בו טבלאות בשם `clients`, `orders`, `payments` שעלולות להתנגש. הקובץ מיועד להקמה ראשונית, לא לשדרוג סכימה קיימת.
2. פתחי את **Authentication → Settings** וכבי הרשמה ציבורית / **Allow new users to sign up**. השאירי התחברות בדוא״ל וסיסמה פעילה אם זה אופן ההתחברות הרצוי.
3. הזמיני כל משתמש בנפרד מתוך **Authentication → Users** (או צרי משתמש דרך ממשק הניהול). אל תשתמשו בחשבון משותף ואל תשלחו סיסמאות בצ׳אט או בקוד. ודאי שהזמנות בדוא״ל מוגדרות; לסביבת עבודה אמיתית מומלץ להגדיר ספק SMTP ולדרוש סיסמאות חזקות ואימות רב־שלבי למנהלת.
4. פתחי **SQL Editor → New query**, הדביקי את תוכן `supabase-schema.sql` והריצי. פעולה זו מקימה טבלאות, מפתחות זרים, אינדקסים והרשאות RLS בלבד; היא **אינה** מחברת את האתר, משנה את הגדרת ההרשמה ב־Auth או מייבאת מידע.
5. אשרי משתמשים רק לאחר שהוזמנו. ב־SQL Editor הריצי עבור כל כתובת שאושרה, לאחר החלפת הכתובת:

   ```sql
   insert into private.approved_users (user_id)
   select id
   from auth.users
   where email = 'user@example.com'
   on conflict (user_id) do nothing;
   ```

   ודאי שהכתובת קיימת ב־Authentication → Users. אם אין התאמה, לא יתווסף משתמש. להסרת הרשאה, מחקי את רשומת המשתמש מ־`private.approved_users`; מחיקת ההרשאה אינה מוחקת את הנתונים.
6. בדקי ב־Table Editor שנוצרו שלוש הטבלאות. בדקי ב־Authentication שההרשמה הציבורית כבויה, וב־Database → Policies שכל הטבלאות מוגנות ב־RLS. **אל** תוסיפי מדיניות `anon`, אל תחשפי את סכימת `private` ב־API, ואל תתני למשתמשי האתר גישה לטבלת רשימת האישור.

## תכנית יבוא בטוחה לנתונים המקומיים

התקנת SQL זו אינה נוגעת ב־`localStorage`. לפני חיבור האתר וביצוע יבוא:

1. שמרי גיבוי נפרד של הערך המלא `modaat-newspaper-ads-v1` מכל דפדפן שבו יש נתונים. אם למזכירה יש עותק מקומי משלה, אספי גם אותו והשווי בין הרשומות; כרגע אין סנכרון בין הדפדפנים.
2. החליטי אילו רשומות הן נתוני אמת. ביבוא שמרי גם רשומות הדגמה או בדיקה קיימות עד שהן נבדקו ואושרה הסרתן — אין למחוק או לדרוס אותן אוטומטית.
3. היבוא העתידי ימפה לקוחות תחילה (`id`, `name`, `phone`, `email`) ואז הזמנות (`id`, `clientId` ← `client_id`, `date` ← `publication_date`, `section`, `amount`, `paymentStatus` ← `payment_status`, `notes`). יש לשמור את מזהי הטקסט המקוריים כדי לשמר את הקשר בין הזמנה ללקוח.
4. לפני השלמת היבוא, להשוות כמויות ומזהים, לוודא שכל `client_id` קיים, לבדוק סטטוסים וסכומים, ולסקור כפילויות/התנגשויות מזהים בין דפדפנים. לבצע את היבוא בעסקה (transaction) ולא לאפס את הטבלאות.
5. כרגע נשמר רק סטטוס `paid`/`pending`, לא תיעוד של תשלומים בפועל. לכן ביבוא הראשון יש לשמר את הסטטוס ב־`orders.payment_status` ולהשאיר את `payments` ריקה — אין להמציא תאריכי תשלום או עסקאות. היסטוריית תשלומים תתווסף רק עם שינוי מתאים בממשק ובקוד.
6. לאחר חיבור עתידי, להשוות את הנתונים באתר מול הגיבוי ולהתחבר מכל שני המחשבים עם משתמשים נפרדים שאושרו. להשאיר את עותקי `localStorage` כגיבוי עד שהיבוא והבדיקות הושלמו.

לתשומת לבך: מחיקת לקוח עם הזמנות קיימות חסומה על ידי קשר המפתח הזר. לאחר שמירת תשלום בפועל, מחיקת ההזמנה שלו תהיה חסומה גם היא כדי לשמור על יומן התשלומים; לפני חיבור יומן התשלומים יש להחליף מחיקה כזו בארכוב/ביטול בממשק.

## לפני חיבור האתר

האתר כרגע הוא HTML/CSS/JavaScript מקומי, ללא לקוח Supabase וללא מסך התחברות. שלב חיבור עתידי ידרוש הוספת Supabase Auth, טעינה ושמירה במסד הנתונים במקום קריאה וכתיבה ל־`localStorage`, טיפול בשגיאות/טעינה, ובדיקת גישה עם משתמש מאושר ולא מאושר.

באתר דפדפן מותר להשתמש רק ב־Project URL ובמפתח **publishable** (או `anon` הישן) של Supabase, עם RLS פעיל. אין להכניס `service_role`, מפתח secret או סיסמת מסד נתונים ל־HTML, JavaScript, Git או קובץ שנשלח למשתמשים. פרטי service-role נשארים בשרת מאובטח בלבד; במבנה הנוכחי אין שרת כזה. חיבור עתידי צריך להיעשות ב־HTTPS, ולא בפתיחת קובץ `file://`.

העיצוב הקיים לא שונה במסגרת הכנת הסכימה וההוראות, והאתר/הנתונים המקומיים לא שונו.
