# גרסת בדיקה מקומית: האתר האמיתי על PostgreSQL אמיתי, עם נתוני בדיקה בלבד

**מה זה:** האתר עצמו (`index.html`, `app.js`, `business-app.js`, `styles.css`) רץ מול PostgreSQL 18 אמיתי (PGlite) שפועל בתוך הדפדפן.

- המסד נבנה מקובצי ה-SQL של הפרויקט, באותו סדר שמתוכנן לייצור:
  schema ← reliability ← business-upgrade ← sheets-and-order-numbers ← **orders-v3** ← **sheets-v2** ← **enforce** ← **cutover**.
  אחרי ההתקנה מורצים קובצי ה-verify.
- RLS, ההרשאות, ה-cutover וכל פונקציות ה-RPC פועלים כמו ב-Supabase.
- **אין חיבור ל-Supabase ואין קשר לייצור.** הנתונים נשמרים רק בדפדפן הזה (IndexedDB) ולא יוצאים מהמחשב.
- בתחתית המסך יש פס אדום: "סביבת בדיקה מקומית". הפס הזה קיים רק בגרסה המקומית ולא באתר.

## הפעלה
**צריך:** Node.js וגם Chrome או Edge.

1. לוחצים לחיצה כפולה על `testing\local-pg\start-local.cmd`. אפשר גם להריץ משורש הפרויקט:
   ```
   node testing/local-pg/start-local.mjs
   ```
2. פותחים את **http://127.0.0.1:8010/**. אם הדף נפתח לפני שהשרת עלה, מרעננים.
3. מתחברים עם **`staff@local.test`** והסיסמה **`test1234`**.
   - חשבון שני מאושר: `second@local.test` / `test1234`.
   - חשבון שלא אושר (לבדיקת חסימה): `pending@local.test` / `test1234`.
4. **בפעם הראשונה** המסד נבנה בתוך כ-10 שניות. אחר כך הוא נשמר בין פתיחות.
   - אם PGlite לא נמצא במחשב, השרת מוריד אותו פעם אחת מ-npm ובודק את החתימה שלו.
5. **עצירה:** Ctrl+C בחלון השרת.

**איפוס:** הכפתור "איפוס נתוני הבדיקה" בפס האדום מוחק את המסד המקומי ובונה אותו מחדש מקובצי ה-SQL. כדאי לאפס אחרי כל שינוי בקובצי ה-SQL, והפס מתריע כשיש שינוי כזה.

**מסד נפרד:** הפרמטר `?db=<שם>` פותח מסד נפרד, למשל `http://127.0.0.1:8010/?db=demo`. בדיקות הקצה-לקצה רצות על המסד `e2e` ולא נוגעות במסד הידני.

## נתוני הבדיקה ההתחלתיים
- **5 לקוחות.** לכל שם יש סיומת "(בדיקה)".
- **3 מוצרים בקטלוג.**
- **6 גיליונות, 501–506:** ימי ראשון הקרובים. כל גיליון נסגר ביום שישי ב-00:00.
- **4 הזמנות:**
  - כספיות: אחת שולמה ושתיים פתוחות.
  - בקרדיטים: אחת.
- **חבילה אחת** עם לוח תשלומים.
- **מונה ההזמנות:** 22354. זו סימולציה של יום המעבר מגוגל שיטס, ולכן ההזמנה הבאה תקבל 22355 ואילך. **בייצור המונה לא שונה.**

## מה כדאי לבדוק ידנית
- **הזמנות:**
  - הזמנה חדשה, כספית או בקרדיטים. אי אפשר לשלב את שתי השיטות באותה הזמנה.
  - עריכה בלחיצה כפולה: פירוט, מחיר, גיליון, סטטוס קובץ וסטטוס שיבוץ.
  - ביטול הזמנה.
- **תשלומים:** תקבול חלקי, השלמה לתשלום מלא וביטול תקבול. אין אפשרות להזין תאריך עתידי.
- **חבילות:** רכישת חבילה מכרטיס הלקוח, עריכת לוח התשלומים והתאמת קרדיטים.
- **גיליונות:** הוספת גיליונות, סגירה ופתיחה מחדש. אי אפשר להזמין לגיליון סגור.
- **התאמת יתרות:** אותה יתרה לתשלום בלוח הבקרה, במסך התשלומים ובדוחות.

## בדיקות אוטומטיות מקצה לקצה
כשהשרת רץ, מריצים בחלון נוסף:
```
node testing/local-pg/run-e2e.mjs
```
הבדיקות מפעילות את המסכים האמיתיים ב-Chrome, ובודקות כל תוצאה ישירות במסד בשאילתות SQL. אפשר גם לפתוח את `http://127.0.0.1:8010/__local/e2e.html` בדפדפן.

## מגבלות (חשוב)
- **זה לא Supabase.** החלקים הבאים מוחלפים כאן בתחליף מקומי:
  - **ההתחברות:** חשבונות בדיקה קבועים.
  - **Realtime:** מתעדכן רק משינויים שנעשו באותו טאב.
  - **PostgREST:** מתורגם בקובץ `pg-supabase.js`.
- **מה שלא נבדק כאן ודורש פרויקט Supabase לבדיקות:**
  - התחברות אמיתית ומדיניות Auth.
  - Realtime בין שני מחשבים.
  - מגבלות קצב.
  - ה-CSP של האתר.
- **טאב אחד:** פותחים טאב אחד לכל מסד. אם צריך שני משתמשים במקביל, פותחים מסדים נפרדים (`?db=`).
- **בלי CSP:** השרת המקומי לא שולח CSP, כי PGlite צריך WebAssembly. ה-CSP של הייצור נבדק בבדיקות ה-Mock (`testing/browser/`).
